# Runtime LoRA для Krea 2 worker

**Дата:** 2026-07-17
**Статус:** согласовано для планирования реализации

## Контекст

`workers/krea2` — thin RunPod Serverless worker без ComfyUI. Он загружает один
Krea 2 Turbo FP8 DiT при старте процесса и использует собственный
`SingleStreamDiT`. FP8 `Linear`-слои сохраняют базовые веса в FP8 и приводят их
к BF16 только внутри `forward`.

Нужно разрешить клиенту выбирать до четырёх заранее скачанных Krea 2 LoRA для
конкретного job. Базовые FP8-веса нельзя необратимо изменять или пересобирать
для каждой комбинации адаптеров.

## Цели

- Поддержать от нуля до четырёх обычных Krea 2 text-to-image LoRA в одном job.
- Принимать отдельный `strength` для каждой LoRA; значение по умолчанию — `1.0`.
- Разрешить диапазон `strength` от `0.0` до `2.0` включительно.
- Загружать с Network Volume только адаптеры, запрошенные текущим job.
- Применять LoRA как runtime-дельты поверх неизменных FP8-весов DiT.
- Освобождать GPU-память адаптеров до VAE decode и после любой ошибки.
- Не хранить в публичном репозитории имена или метаданные пользовательских LoRA.

## Не входит в scope

- Edit, ControlNet, depth, reference-image и другие функциональные адаптеры.
- LoRA для text encoder или VAE.
- LyCORIS, LoHa, LoKr, DoRA и другие форматы, отличные от обычной low-rank LoRA.
- Скачивание LoRA по URL во время job.
- CPU/GPU-кэш адаптеров между job.
- Публичный API для получения списка доступных LoRA.
- Автоматический GPU smoke test в этом репозитории.
- Хранение display name, рекомендуемого strength, trigger words или иных
  клиентских метаданных. Эти данные принадлежат клиентскому репозиторию.

## Файловый каталог и allowlist

Worker использует каталог:

```text
/runpod-volume/krea2/loras/
  lora_a.safetensors
  lora_b.safetensors
```

Путь настраивается переменной `LORA_DIR`; значение по умолчанию —
`$MODEL_DIR/loras`, что при стандартной конфигурации соответствует пути выше.

При старте процесса worker сканирует только файлы `*.safetensors` в корне
каталога. Stem файла становится публичным ID:
`lora_a.safetensors` превращается в `lora_a`.

Сканирование строит внутренний словарь `ID -> Path`, но не загружает тензоры.
Клиентское значение `name` никогда напрямую не конкатенируется с путём: файл
можно получить только через этот словарь. Дубликаты ID и некорректные имена
приводят к ошибке инициализации. Подкаталоги не сканируются.

Каталог фиксируется на время жизни процесса. После добавления или удаления
файлов существующий тёплый worker нужно перезапустить; новый worker увидит
актуальное содержимое volume при старте.

## API

Обычная генерация не требует поля `action`:

```json
{
  "input": {
    "prompt": "portrait, cinematic light",
    "loras": [
      {"name": "lora_a", "strength": 0.8},
      {"name": "lora_b"}
    ]
  }
}
```

Поле `loras` необязательно и по умолчанию равно пустому списку. Каждый элемент
имеет обязательную строку `name` и необязательное числовое поле `strength`.
Нормализованный default для `strength` — `1.0`.

Правила валидации:

- не более четырёх элементов;
- все имена должны быть уникальны;
- каждое имя должно присутствовать в startup allowlist;
- `strength` должен быть конечным числом в диапазоне `0.0..2.0`;
- boolean не считается допустимым числом;
- строки, URL, абсолютные пути и компоненты пути не принимаются вместо ID.

Адаптер со `strength: 0.0` считается отключённым: его файл не читается, и он не
включается в список фактически применённых адаптеров.

Успешный ответ дополняется нормализованным списком реально применённых LoRA:

```json
{
  "loras": [
    {"name": "lora_a", "strength": 0.8},
    {"name": "lora_b", "strength": 1.0}
  ]
}
```

Отдельного `list_loras` action или endpoint нет.

## Компоненты

### `LoRACatalog`

Один раз сканирует `LORA_DIR`, строит allowlist и разрешает ID в заранее
проверенный путь. Компонент не читает safetensors и не знает клиентских
метаданных.

### `LoRALoader`

На каждый job читает только выбранные файлы через `safetensors`, распознаёт
поддерживаемые пары A/B, alpha и сопоставляет их с именованными `Linear`-слоями
`SingleStreamDiT`.

Поддерживаемые обычные соглашения:

- `lora_down.weight` + `lora_up.weight`;
- `lora_A.weight` + `lora_B.weight`;
- необязательный scalar `alpha`, по умолчанию равный rank.

Для Krea 2 loader поддерживает распространённые префиксы `diffusion_model.`,
`transformer.` и отсутствие префикса. Маппинг Diffusers/Comfy-style имён в
native-модули Krea 2 реализуется локально для этой архитектуры; код ComfyUI не
вендорится.

Каждая пара обязана:

- сопоставиться с существующим `nn.Linear` внутри DiT;
- иметь совместимые input/output dimensions;
- иметь согласованный rank;
- быть полностью распознана вместе со своим alpha, если alpha присутствует.

Loader требует хотя бы одну валидную пару и запрещает частичное применение:
неизвестная LoRA-пара или несовпадение формы отклоняет весь job. Это исключает
тихую генерацию с частично проигнорированным адаптером.

### Runtime-compatible Linear

Текущий FP8 `forward` расширяется контролируемым runtime-слоем. Для каждого
активного адаптера Linear вычисляет:

```text
base_output = linear(x, fp8_weight cast to compute dtype, bias)
lora_output = B(A(x)) * (alpha / rank) * strength
output = base_output + sum(lora_output)
```

LoRA-вычисления выполняются в BF16. Базовый `Parameter` не заменяется, не
модифицируется и не переквантуется. Та же обвязка корректно обрабатывает
не-FP8 Linear, если LoRA нацелен на такой слой.

### `LoRAActivation`

Контекстный менеджер владеет CPU-тензорами текущего job. После завершения text
encoding и offload text encoder он переносит A/B на устройство DiT, подключает
их к соответствующим runtime Linear и активирует denoise.

Контекст охватывает только Euler denoise loop. В `finally` он снимает все
адаптеры, удаляет GPU-ссылки и освобождает CUDA cache. Контекст завершается до
VAE decode, поэтому LoRA не увеличивают пик памяти декодера.

### Блокировка

Pipeline использует process-local lock на весь участок `activate -> denoise ->
deactivate`. Это предотвращает смешивание адаптеров, если один процесс когда-либо
начнёт обслуживать несколько job конкурентно. Несколько RunPod worker-процессов
и pod работают независимо.

## Поток одного job

1. Handler валидирует обычные поля и нормализует `loras`.
2. `LoRACatalog` разрешает имена в пути.
3. `LoRALoader` читает выбранные файлы в CPU RAM и валидирует все пары.
4. Pipeline кодирует prompt обычным text encoder.
5. Text encoder выгружается на CPU.
6. `LoRAActivation` переносит адаптеры в GPU и подключает их к DiT.
7. DiT выполняет denoise с суммой максимум четырёх runtime-дельт.
8. Контекст гарантированно отключает LoRA и освобождает их GPU-память.
9. VAE декодирует latent без LoRA в VRAM.
10. Handler возвращает изображения и нормализованный список применённых LoRA.

При пустом `loras` шаги загрузки и активации полностью пропускаются.

## Ошибки и восстановление

До генерации возвращается понятная клиентская ошибка для:

- неизвестного ID;
- слишком большого списка или дубликатов;
- некорректного strength;
- повреждённого safetensors;
- неподдерживаемого типа адаптера;
- неизвестных ключей или несовместимых tensor shapes.

Ошибки содержат имя LoRA и безопасное описание причины, но не раскрывают
абсолютный путь volume. Ошибки входа и формата не требуют `refresh_worker`, так
как базовая модель остаётся пригодной для следующего job.

При CUDA OOM или неожиданном исключении `LoRAActivation.__exit__` выполняет
cleanup до существующей обработки ошибки в handler. CUDA OOM сохраняет текущее
поведение `refresh_worker: true`.

## Память и производительность

- На cold start добавляется только дешёвое сканирование имён файлов.
- Network Volume читается только для LoRA текущего job.
- Одновременно в CPU/GPU находятся не более четырёх выбранных адаптеров.
- Между job тензоры LoRA не кэшируются в первой версии.
- Runtime-дельты добавляют matmul для каждой активной пары и каждого denoise
  шага; это сознательный обмен небольшой latency на неизменность FP8-модели и
  предсказуемое переключение комбинаций.

## Проверки в публичном репозитории

Автоматические тесты не требуют реальных пользовательских LoRA или GPU:

- сканирование каталога и построение allowlist;
- отсутствие обхода пути через клиентское имя;
- валидация списка, default strength, диапазона, дубликатов и лимита четыре;
- распознавание обеих поддерживаемых схем A/B и alpha;
- маппинг Krea 2 имён и отказ при неизвестном ключе или неверной форме;
- математическая проверка на маленьком CPU Linear:
  `base(x) + sum(strength * alpha/rank * B(A(x)))`;
- одновременное суммирование нескольких адаптеров;
- cleanup runtime-состояния после успеха и искусственного исключения;
- неизменность базового вывода до и после LoRA activation.

GPU smoke test и реальные имена LoRA в этот репозиторий не добавляются.
Интеграционную проверку реальной генерации выполняет владелец из клиентского
репозитория, который хранит имена, рекомендуемые strength и trigger words.

## Критерии готовности

- Job без `loras` сохраняет прежнее поведение worker.
- Job с одной-четырьмя валидными text-to-image LoRA успешно доходит до denoise.
- Strength по умолчанию и диапазон соответствуют API-контракту.
- Базовые FP8-веса не изменяются при активации и деактивации.
- LoRA отключаются до VAE decode и после любой ошибки.
- Невалидный адаптер не применяется частично.
- Публичный репозиторий не содержит пользовательских имён или метаданных LoRA.
