The sequence was Edit → Turbo → Edit with two references → Edit with four
references → Edit with a larger reference budget → Turbo. Both Turbo outputs matched byte-for-byte, SHA-256
`dba75d25b500a24f9bab2de97a194f8ac57b33d1a8a0408b4cd2ddf8aa4c56c4`, demonstrating that Edit adapter/cache state did
not alter later Turbo requests. The source fixtures depict a teapot and cup;
the fourth reference repeats the first. These checks establish execution with
multiple references, not multi-identity preservation or general editing quality.
Output images were visually inspected separately. The default single-reference
test recolored the teapot but changed composition substantially. The otherwise
matching `edit-detail` request retained a 1.048576 MP reference and preserved
the original framing much better. This provides a useful setting for that
1024×1024 fixture, not a universal quality guarantee. The two-reference edit
was recognizable, while the four-reference result rendered the original photo
inside a frame and did not perform the requested recoloring. Accepting four
references is therefore distinct from reliable four-reference instruction
following; this community adapter's multi-reference quality remains limited.

Timings include model/adapter preparation when required and exclude queue
delay. This was functional verification, without GPU calibration or a measured
cold-start improvement claim.
